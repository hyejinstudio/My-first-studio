**입력 (Chromium 실제 이벤트: 마우스 / CDP 터치 / 키보드)**
- 미리보기 = 자른 각도: 실제 마우스로 16개 경로(천천히 0/±10/25/−33, 왼쪽으로 긋기, 45°→35 고정, 100ms 휙 긋기, 떼는 순간 50px 튐, 원호로 돌리면서 떼기 5회)를 그었다. 놓기 직전 그린 프레임의 `previewAngle()`과 자른 φ가 16/16 같았다. 떼는 순간의 튐은 무시된다.
- 40px: 39·39.9px → 취소, 40·41px → 자름. 반올림: 2.5° → 3, −2.5° → −3, 0.49° → 0, 0.5° → 1, 34.5 이상과 수직 → ±35.
- iPad 터치(CDP): 기본 끌기·떼기 정상. 두 번째 손가락이 닿아 움직여도 무시되고, 첫 손가락을 뗄 때 첫 손가락 각도로 자른다. 두 번째 손가락을 먼저 떼도 영향 없음. touchcancel → 취소. 화면 밖으로 끌고 나가서 떼도 정상으로 자름. 톡 치기 → 자르지 않음. 40px 안으로 되돌아와 떼기 → 취소. 끄는 중 화면 숨김·blur → 취소 후 일시정지, 자르지 않음.
- 길게 누르기·선택: contextmenu는 preventDefault, body는 user-select:none, 무대는 touch-action:none. 마우스 오른쪽 버튼으로는 끌기가 시작되지 않는다.
- 키보드: ← 1번 = +1°, → = −1°. 0.5초 누르면 16°(1 + 60×0.25), 2초 누르면 −35에서 멈춘다. 스페이스로 자르고, 다음 마디에서 칼이 0°로 돌아온다. 겨누기 밖의 스페이스는 무시. 끄는 중 ←→ 무시. Enter로 시작, Esc/P로 일시정지와 재개, M으로 음소거.
- 버튼 포커스 상태에서 스페이스: 음소거 버튼에 포커스가 있거나 마우스로 누른 직후에도 스페이스는 자르기로만 쓰이고 음소거가 바뀌지 않는다.

**학습 흐름 (저장소를 비운 첫 판, iPad 세로)**
- 1마디 θs=0, 손가락 힌트·정답 점선·평행 빛 표시. 누르면 손가락 힌트가 사라진다.
- 2마디 θs=+10, 손가락·점선. 3마디 θs=−10, 손가락은 있고 점선은 없다.
- 4마디: 갈색 맥박과 ✕가 0.8초, 평행 빛 꺼짐. 두 번째 판에서도 표시된다(개발자 변경. design.md의 "끄는 힌트" 목록에 4마디는 없으므로 명세와 맞다).
- 톡 치기 → 손가락 힌트가 즉시 1회 다시 나온다. 4마디에서 겨누기 시간 절반까지 입력이 없으면 손가락 힌트가 나온다.
- 두 번째 판: 손가락 힌트 없음. 1·2마디 점선과 1~3마디 평행 빛은 유지.
- 해설 카드: 어긋남·무름(정면 / 비스듬함)·말라 버림이 종류마다 1번만 뜬다. 숫자를 확인했다: 어긋남 13°(e=13), 무름 9mm(s−u=9.24), 비스듬한 무름 2mm(2.47), 1mm(0.81). 같은 종류의 두 번째 실패부터는 카드 없이 작은 꼬리표만 뜬다(17°, 1mm, 8mm 실제 값과 일치). 0.8초 잠금 중의 탭은 무시되고, 잠금 후 탭이나 스페이스로 닫힌다. 말라 버림 카드에는 손가락 그림이 나온다.
- 판을 끝내는 실패(3번째 실패)는 카드를 띄우지 않고 기록하지도 않는다. 다음 판에서 처음 그 실패가 나올 때 뜬다(개발자 변경). 쓰러지는 연출을 카드로 끊지 않고 해설 기회도 잃지 않으므로 타당하다고 본다.

**밸런스 — 봇 재측정 (독립 구현)**
design.md 봇 규칙을 따로 작성해 시드 1~400으로 돌렸다. 개발자 표와 같은 결과가 나왔다: 초보 582 / 보통 1,166 / 숙련 1,844(완주 44%, 60초) / 욕심 큼 657 / 키보드 1,679. 원래 규칙(m ≤ g)으로 돌리면 키보드 봇은 1,075·무름 1,195회로 떨어지고, 나머지는 거의 같다.
- **봇 규칙 0<m≤g 변경은 타당하다.** 원래 규칙은 "준비 시간이 끝난 순간 이미 갈색 안이면 그 자리에서 자른다"는 뜻이 되는데, 사람은 그렇게 하지 않는다. 이 변경으로 실제로 달라지는 것은 키보드 봇뿐이다.
- 초보 중앙값 582(목표 250~500): **대부분 봇 모델 한계로 본다.** 봇은 규칙을 완벽히 알고 각도만 흔들린다(σ 5.5°). 사람 초보는 "어떻게 자르나"를 몰라 생기는 말라 버림·조기 실패가 있다(봇의 말라 버림은 0회). 다만 초보도 붙이기만 하면 마디당 40~60mm가 붙는 구조라 실제로도 쉬운 쪽일 수 있다. 실기기 체감 확인 항목이다.
- 욕심 큼 p90 < 숙련 p90: **봇 모델 한계다.** g=2mm에 타이밍 오차 σ 0.045초를 주면 접수가 최대 약 107mm/s로 움직이므로 마디마다 무름 30% 이상이 된다(무름 1,200 / 실패 1,200). 이렇게 행동하는 사람은 없으므로 밸런스 문제로 보지 않는다.
- 숙련 판 길이 60초(목표 75~95): **봇 모델 한계다.** 봇은 첫 내려감에서 바로 자른다(겨누기 약 0.5초). 고정 연출이 판당 약 50초(내가 cutNow로 즉시 자르며 30마디를 돈 실제 시간도 약 50초)라서, 사람의 겨누기를 1.0~1.5초로 잡으면 80~95초가 된다. 사람 실측이 필요하다.
- 시드 운 폭: 게임 시드 80개 × 봇 시드 200개로 시드별 **평균**을 보면 p10~p90 폭 115mm다(같은 시드를 반복한 순수 잡음 폭은 49mm, 따라서 실제 시드 효과는 약 100mm). 목표 150mm 안이다. 중앙값-of-5 기준의 486mm는 봇 잡음 때문이다. 시드 효과는 "흔들림 방향이 면 기울기와 같은 마디 수"와 상관 0.72를 보인다. 이 봇은 흔들림을 기다려 쓰지 않으므로, 기다릴 줄 아는 사람에게는 시드 운이 더 작을 것으로 추정한다.

### 버그
- [보통] **localStorage가 막힌 환경에서 해설 카드가 실패할 때마다 뜬다**
  - 증상: 저장소 접근이 예외를 던지면(iPad Safari "모든 쿠키 차단" 등) 같은 종류의 실패라도 매번 게임이 멈추고 해설 카드와 0.8초 잠금이 나온다. 같은 원인으로 결과 화면의 "새 기록" 알약도 매 판 나온다.
  - 재현: `localStorage` 접근이 SecurityError를 던지게 한 init script로 연다. 어긋남을 두 번 내면 두 번 다 카드가 뜬다. 무름·말라 버림도 마찬가지(t9-cards.js block 실행에서 7번 실패 중 7번).
  - 기대: 기기당(저장이 안 되면 최소한 이 페이지 세션 안에서) 종류별 1번만 뜬다.
  - 위치: `explainWanted()`(2291행). `readExplained()`가 매번 저장소만 읽는다. 메모리 사본(예: `G.explained`)에 함께 기록하면 된다. 최고 기록도 `readBest()`가 null이라 매번 isNew가 된다(2680행 부근 showResult).
- [낮음] **겨누기가 시작된 직후 한 프레임 안에 손을 떼면 무시된다(스페이스는 같은 순간에 잘림)**
  - 증상: 접수가 내려오는 동안 미리 끌어 두고, 겨누기가 시작된 뒤 다음 화면 갱신 전(≤ 약 16ms)에 떼면 자르지 않는다. 칼은 남아 있어 다시 끌어야 한다. 같은 창에서 스페이스는 자른다.
  - 재현: t6-edge.js. gotoSeg 후 끌기, 겨누기 시작 +3ms에 같은 작업 안에서 pointer up → 6/6 안 잘림, 같은 조건의 스페이스 6/6 잘림.
  - 기대: 떼는 시각이 겨누기 안이면 자른다(design "입력 시각은 [겨누기 시작, 현재]로 자른다").
  - 위치: `ptrUp()`(2396~2402행)에 `G.run.advanceTo(t)`가 없다. `ptrDown`·`keyInput`은 호출하고 있다.
- [낮음, 명세대로지만 사람 쪽 위험] **아주 빠른 "휙 긋기"는 취소되거나 처음 방향으로 잘린다**
  - 증상: 50ms 전 기준점 규칙 때문에 생긴다. 150px을 70ms 이하로 그어 떼면 취소된다(톡 치기로 처리: 취소음, 첫 판이면 손가락 힌트). 80px을 100ms에 그어도 취소된다. 휘어지는 빠른 엄지 궤적(반지름 250px, 현 방향 10°)은 90ms면 21°, 120ms면 18°, 300ms면 13°로 잘린다. 궤적 전체 방향이 아니라 앞부분 방향을 따른다.
  - 판단: 미리보기와 자른 선은 항상 같으므로 "보인 것과 다르게 잘림"은 아니다. 다만 화면을 볼 틈이 없는 빠른 긋기에서는 억울할 수 있다. 데모와 힌트가 "끌어 두고 → 기다렸다 → 뗀다"를 가르치므로 대부분의 사람은 이 경우에 들지 않을 것으로 추정한다. 실기기 확인 2번과 함께 본다.
  - 위치: `Ctl.refAt`·`angleAt`(1191~1201행), 명세 "끌기 → 각도 계산" 3·7.
- [낮음] **시작 화면 뒤로 위쪽 바가 비친다(폰 가로에서 가장 눈에 띔)**
  - 증상: 844×390에서 제목 옆에 옅은 "장 키우기2 … 1/30"과 하트·버튼 윤곽이 보인다. 실제로 겹치거나 잘리지는 않는다.
  - 재현: shots/phL-light-0start.png. iPad 세로에서도 옅게 보인다.
  - 기대: 시작 화면에서는 위쪽 바를 숨기거나 더 불투명하게 가린다.
  - 위치: 시작 overlay(#ovStart) 배경의 투명도 / 위쪽 바 표시.
- 참고(버그 아님): design.md QA 7의 "최대 69.3mm"는 흔들림 α를 빼고 계산한 값이다. 실제 최대는 70.6mm로 여전히 80보다 작다. 문서 숫자만 고치면 된다.
