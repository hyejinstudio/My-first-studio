# 증거 조작범 기획서
- slug: fake-evidence
- 한 줄 소개: 사건 현장의 증거 6개 중 누군가 조작한 가짜 1개를 찾고, 왜 가짜인지까지 밝혀라.
- 원안: 사용자 기획 「3. 증거 조작범」(증거 6개 비교 → 가짜 1개 클릭 → 조작 이유 선택). 규칙·흐름은 원안 그대로, 수치·데이터만 보강.
- 사건 데이터: `docs/games/fake-evidence/cases.json` (15건). 개발자는 이 JSON을 `games/fake-evidence/index.html` 안 `<script type="application/json" id="cases">`에 그대로 넣는다(외부 fetch 금지).

## 핵심 루프
1. **사건 카드** (1.2초, 탭하면 바로 넘김): "사건 2 / 5 · 정전된 빵집" + 아이콘.
2. **수사 화면** (한 화면): 위 = 현장 한 줄(story) + 추가 정보 2~4줄(facts, 번호 ①②③④). 아래 = 증거 카드 6장(아이콘 + 이름 + 세부 1~2줄, **처음부터 모두 펼쳐 보임** — 따로 열 필요 없음).
3. **가짜 고르기**: 카드 탭 = 선택(다른 카드 탭하면 바뀜). 선택하면 아래에 이유 4개(A~D)가 나타남.
4. **이유 고르기** → "고발하기" 버튼(증거·이유 둘 다 골라야 활성). 고발 전까지는 증거·이유 모두 바꿀 수 있음. 중간 정답 피드백 없음.
5. **판정·해설**: 가짜 카드에 "조작" 도장 → 가짜 카드와 근거 정보(link.facts)·근거 증거(link.evidence)를 같은 색 테두리 + 연결선으로 표시 → explain 1~2줄. 이유를 틀렸으면 정답 이유와 내가 고른 이유의 `why` 표시. 판정 화면에서 아무 카드나 탭하면 그 카드의 `note`(왜 진짜/가짜인지) 표시.
6. "다음 사건" → 5건 끝나거나 기회 0이면 결과 화면.

- 한 판 = 사건 5건, 목표 5~7분(사건당 약 60~80초).
- 튜토리얼 화면 없음. **첫 판(최고 기록 없음)의 1번 사건은 항상 c01 「잠긴 미술실」**(원안 예시, 가장 쉬움)로 고정 → 플레이 자체가 예시. 첫 사건 수사 화면 위에 한 줄 안내만: "가짜 증거 1개를 고르고, 이유를 고르세요."

## 규칙 (승리/패배, 점수)
| 결과 | 점수 | 기회 |
|---|---|---|
| 증거 O + 이유 O | (100 + 60 + 시간 보너스) × 배수 | 유지 |
| 증거 O + 이유 X | 100 × 배수 (시간 보너스 없음) | 유지 |
| 증거 X | 0 (이유는 채점 안 함) | −1 |

- 배수: 쉬움 ×1, 복합 ×1.5, 함정 ×2 (결과는 반올림 정수).
- 시간 보너스(증거·이유 모두 맞을 때만): 수사 화면이 뜬 순간부터 "고발하기"까지 t초. `40 × clamp((120 − t) / 80, 0, 1)` 반올림 → 40초 이내 40점, 120초 이상 0점. **제한 시간 없음**(압박 없이 읽게), 화면에 작은 경과 시계만.
- 기회(돋보기 아이콘) 3개. 0이 되면 그 사건 판정 후 "수사 종료" → 결과 화면.
- 완벽 보너스: 5건 모두 증거·이유 정답이면 +200.
- 이론상 최대: 쉬움 200 + 복합 300×2 + 함정 400×2 + 200 = **1800**.
- 결과 화면: 총점, 사건별 결과(○ 완벽 / △ 증거만 / × 실패) + 사건 이름, 최고 기록, "다시 수사", 순위표 버튼.
- 최고 기록: `localStorage['fake-evidence-best']` (정수).
- 직전 판 사건 id: `localStorage['fake-evidence-last']` (JSON 배열, 반복 방지용).

### 온라인 순위표
- `lib/leaderboard.js`, game key `'fake-evidence'`. 판이 끝날 때(5건 완료 또는 수사 종료) `Leaderboard.report({game:'fake-evidence', score, eligible})`. score < 1이면 보내지 않음.
- `eligible = false`: 테스트 훅으로 사건 지정·시간 조작을 한 판.
- 순위 점수 = 위 총점. 이론상 최대 1800 → **score_cap 2000 제안**(여유 포함).

난이도 정의
- **쉬움(tier 1)**: 가짜 증거가 추가 정보 1줄과 바로 부딪침(시간·날씨·정전 등).
- **복합(tier 2)**: 정보 2줄 또는 정보 + 다른 증거를 합쳐야 보임(출발 + 소요 시간, 개막일 + 전날 설치 등).
- **함정(tier 3)**: 그럴듯한 오답 이유가 각각 다른 수상한 증거를 겨냥하고, 그 증거들은 세부·정보에서 해명됨. 계산(요일, 속도)이나 숨은 조건(오프라인 결제, 눈 그친 시각)이 필요.

## 콘텐츠

### 사건 데이터 스키마 (cases.json)
```
{ id, tier(1|2|3), title, icon(이모지), story,
  facts: [{id:"f1", text}],            // 2~4개, 믿을 수 있는 정보
  evidence: [{name, icon, detail, note}], // 정확히 6개, note = 판정 후 해설
  fake: 0~5,                           // 데이터 순서 기준 인덱스
  reasons: [{text, correct, why?}],    // 정확히 4개, correct 1개, 오답엔 why
  explain,                             // 판정 해설 1~2줄
  link: { facts:[fact id], evidence:[데이터 인덱스] } } // 가짜와 모순되는 근거
```
- 게임은 섞은 뒤에도 원래 인덱스를 기억해 link를 표시한다.
- 오답 이유는 대부분 **다른 증거를 겨냥한 그럴듯한 오해**다. 그래서 이유 목록을 봐도 정답 증거가 드러나지 않는다.
- 판정: 이유는 증거가 맞았을 때만 채점한다(증거 X면 이유 무시). 즉 "가짜 증거 + 그 증거의 이유"가 짝이 맞아야 완벽.

### 이유 작성 규칙 (2026-11-15 B-2 반영)
이유 4개는 어느 카드를 지목해도 같은 목록이 뜬다. 목록만 읽고 "사실과 맞는 문장 1개"를 고르면 풀리지 않도록 한다.
- **정답 이유**: 증거 이름·고유 시각을 되도록 말하지 않고, 추가 정보에서 나온 **조건**으로 쓴다(예: "4시엔 정전이라 콘센트 전기가 끊겨 있었다", "새 우표는 1월 7일에야 처음 팔렸다"). 이 조건에 걸리는 것처럼 보이는 진짜 증거가 1개 이상 있게 하고, 그 진짜 증거는 **카드 세부(detail)** 에 해명 단서를 둔다(손잡이식 금전등록기, 365일 ATM, 무인 반납함, 일반 우표 엽서 등).
- **강한 오답** (형태 둘 중 하나):
  (a) 전제는 정보와 맞는 참이고 그럴듯한 모순을 지적하지만, **다른 진짜 증거**를 겨냥하며 그 증거의 세부를 읽으면 풀린다.
  (b) 전제는 참이지만 결론이 틀린 계산·독해 함정(사흘째 날짜 세기, 첫 월요일 6일 vs 7일, 종만 멈춤 vs 시곗바늘, 일정 속도 가정 등).
- **약한 오답**: 상식으로 바로 반박되거나 "수상하다" 수준.
- 단계별 최소: 쉬움 = 강한 오답 2개 + 약한 1개 허용 / 복합 = 강한 2개 이상 / 함정 = 3개 모두 강하게.
- 오답마다 `why`는 "어느 정보·세부 때문에 모순이 아닌지"를 한 줄로.
- **형식 섞기 (B-9)**: 정답만 "조건 문장"이고 오답은 모두 "~할 수 없다" 결론 문장이면 형식만 보고 고를 수 있다. 사건마다 4개 중 조건형(~였다/~이다/~야 한다)과 결론형(~할 수 없다/~리 없다)을 섞고, 정답도 사건에 따라 결론형으로 쓴다. 4개 길이는 비슷하게(20~35자).
- **가짜 겨냥 오답 (B-9)**: 사건마다 오답 1개는 **정답 가짜 카드를 틀린 근거로** 겨냥한다(지나친 일반화, 세부 오독, 요일·시각 계산 실수, 범인 단정 등). 그래야 "오답이 겨냥한 카드 3장 빼기"로 가짜가 남지 않는다. 판정상 이 오답은 '증거 맞음 + 이유 틀림(부분 점수)'이 된다.
- 추가 정보가 오답을 한 문장으로 바로 반박하면 약한 오답이 된다 → 해명 단서는 가능하면 **카드 세부**로 옮긴다(c06 카페 칸, c12 와이파이 문장, c13 벽난로).

### 원안 예시(잠긴 미술실) 정합성 점검 → c01
원안 그대로면 정답이 여러 개로 갈림:
- "오후 8시 사진에 햇빛"이 **추가 정보**에 있으면 믿을 정보가 되어, 가짜가 아니라 '비가 왔다'는 정보와 정보끼리 충돌한다. → 햇빛 묘사를 **증거 6번 세부**로 옮김.
- "저녁 8시에 햇빛"만으론 계절에 따라 애매 → 정보 "해는 오후 6시 10분에 졌다" 추가.
- 3번 "오후 7시 CCTV"는 5시에 잠긴 미술실과 부딪쳐 보임 → **정문 CCTV**, 우산 쓴 사람(비와 맞음)으로 명시.
- 5번 "오전 10시 출입증"은 시간 모순으로 보임 → "하루 종일 쓸 수 있는 방문객 출입증, 미술실 열쇠와 무관"으로 명시.
- 4번 "피해자의 휴대폰"은 내용이 없어 판단 불가 → "마지막 통화 오후 4:50(잠그기 전)"로 보강, 피해자 = 그림 주인 미술 선생님.
- 1·2번(진흙, 젖은 발자국)은 비 + 창문 침입으로 자연스럽게 설명.
- 이유 오답 3개는 사용자가 지적한 의심 지점(잠긴 뒤 사진, 오전 출입증, 잠긴 뒤 CCTV)을 그대로 함정으로 사용.

### 정답 유일성 체크리스트 (모든 사건 필수)
1. 가짜 증거는 facts(또는 facts + 진짜 증거)와 **명백히** 모순된다. 상식은 한 단계까지만(예: 언 호수엔 물결 없음).
2. 진짜 증거 5개 각각에 `note`로 "왜 모순이 아닌지" 한 줄 설명이 있다.
3. facts끼리, 진짜 증거끼리 모순이 없다.
4. 정답 이유는 link에 적힌 정보만으로 성립한다.
5. 오답 이유 3개는 각각 `why`로 반박되며, 정답 이유와 같은 뜻이 아니다.
6. 가짜 증거를 다른 증거로 바꿔 넣어도 정답 이유가 성립하지 않는다.
7. 폭력 묘사 없음(도난·파손 사건만), 실존 작품·캐릭터 없음.
- 위 15건은 이 기준으로 작성·점검함. 사건 추가 시 같은 체크를 거친다.

### 문장 길이 기준
story ≤ 40자, fact ≤ 50자(24자 권장), evidence.name ≤ 12자, detail ≤ 45자, reason ≤ 35자 내외(최대 40자), explain ≤ 60자. 문장은 짧은 평서문.

### 데이터 검증 (validate() 및 Node 스크립트 아이디어 `tests/validate-fake-evidence.js`)
- HTML의 `#cases` JSON과 `docs/games/fake-evidence/cases.json`이 같은지 비교.
- id 중복 없음, tier ∈ {1,2,3}, 단계별 ≥ 5건(한 판 추출 가능), c01 존재.
- evidence 정확히 6개, 각각 name·icon·detail·note 비어 있지 않음, 이름 중복 없음.
- fake ∈ 0..5. reasons 정확히 4개, correct 정확히 1개, 오답마다 why 있음, 문장 중복 없음.
- facts 2~4개, fact id 중복 없음. link.facts ⊆ fact id, link.facts 1개 이상. link.evidence ⊆ 0..5이고 fake 미포함.
- 문장 길이 기준 초과 시 경고.
- 시뮬레이션: 매 사건 `answer()`로 완벽 플레이(setElapsed 0) → 총점 1800, 전부 오답 → 3번째 사건에서 종료, 증거만 정답 → 시간 보너스 0 확인.
- 정답 '유일성' 자체는 자동 증명 불가 → 체크리스트(위) 수동 검토 + 각 진짜 증거의 note 존재로 대신한다.

## 서버 SQL (Supabase SQL Editor에서 Run, 여러 번 Run 안전)
```sql
create or replace function public.score_cap(p_game text)
returns integer language sql immutable set search_path = public as $$
  select case p_game
    when 'poop-rain'     then 50000
    when 'mole-pop'      then 10000
    when 'bunny-ten'     then 170
    when 'snake-garden'  then 4000
    when 'block-stack'   then 5000000
    when 'parrot-beat'   then 60000
    when 'bungeo-easy'   then 1000
    when 'bungeo-normal' then 1000
    when 'bungeo-hard'   then 1000
    when 'fake-evidence' then 2000
    else null end;
$$;
revoke all on function public.score_cap(text) from public, anon, authenticated;
```
- 확인: `select public.score_cap('fake-evidence');` → 2000. SQL 적용 전에는 서버가 이 게임 점수를 거부(cap null)하므로, 게임은 순위표 없이도 정상 동작해야 한다.
